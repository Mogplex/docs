title: Coverage and Triggerability
description: Learn why GitHub sign-in is not the same as GitHub App coverage, how Mogplex labels connection state, and what makes a repo actually trigger-ready.
---

Most setup confusion in Mogplex comes from mixing up three different states:

- GitHub account connected
- installation linked to you
- repo triggerable for webhook-backed work

Those are related, but they are not the same thing.

## Sign-in is not enough

GitHub sign-in (GitHub OAuth) identifies you and reads your org memberships. It
does not give Mogplex access to repositories.

Repository access and webhook-backed routing both come from a GitHub App
installation linked to you. Until one is linked, you can use only repositories
shared to your Mogplex team. See
[Who can link an installation](/web/installations#who-can-link-an-installation).

Self-hosted deployments without a GitHub App are the exception: there, GitHub
OAuth lists and imports repositories, but webhook-backed routing is not
available.

## What "triggerable" actually means

Operationally, a repo becomes triggerable when Mogplex can associate it with a
real GitHub App installation id.

That installation id is the bridge between:

- GitHub webhook events
- synced repos in Mogplex
- installation-scoped routing surfaces

Without that bridge, Mogplex can see the repo but cannot safely route
App-backed automation into it.

## Two different state layers

Mogplex exposes both a user-level GitHub state and a repo-level coverage state.

### User-level GitHub state

The account connection can show up in states like:

| State | Meaning |
| --- | --- |
| `OAuth only` | GitHub sign-in is connected, but no installation is linked to you. You have no repository access of your own yet. In a self-hosted deployment without a GitHub App, this is the normal connected state. |
| `Install pending` | The App install was started, but no installation is linked to you yet. If it stays here after you finish on GitHub, see [An org you belong to does not appear](/web/installations#an-org-you-belong-to-does-not-appear). |
| `App installed` | Coverage exists, but no covered repos are synced into Projects yet |
| `Ready` | App coverage is active and covered repos are already synced |

These are account signals, not repo signals.

### Repo-level coverage state

Each repo effectively falls into one of these buckets:

| Repo label | Meaning |
| --- | --- |
| `Trigger-ready` | The repo has a `github_installation_id` and can participate in App-backed routing |
| `Synced only` | The repo is in Projects, but has no App coverage and no installation is linked to you |
| `Not covered` | An installation is linked to you, but none of your linked installations covers this repo |

With a GitHub App, once an installation is linked to you, the Projects list
shows only repos covered by a linked installation, so listed repos are
`Trigger-ready`. Repos that no linked installation covers are hidden from the
list. You see them as `Not covered` only when you open one directly or show
hidden repos. To fix it, add the repo to the installation on GitHub, or install
the App on the account that owns it.

`Synced only` appears in a self-hosted deployment without a GitHub App, or for
older repo rows while no installation is linked to you.

This is the state that matters when the question is "will this route wake up?"

## What the installations surface exposes

The installations data shown in [Settings](/web/settings) exists to answer a
very practical question:

"Which GitHub owner scopes are actually available for App-backed automation?"

Each installation surfaces:

- account or org login
- scope label such as `Org`, `User`, or `Account`
- synced repo count for the installation
- a GitHub manage link when the metadata is complete enough to build one
- the repos Mogplex currently associates with that installation

If installation metadata is incomplete, Mogplex will try to refresh it from
GitHub before presenting the final view.

## Discovery can fill in missing installation state

Mogplex does not only rely on the install callback.

Each time you open **Settings → Account**, Mogplex looks for installations on
your own account and on your GitHub orgs, and links the ones you own. Orgs that
restrict third-party OAuth apps are not visible to discovery. A GitHub webhook
can also link an installation when you install the App or add repositories to
it. See
[How an installation gets linked](/web/installations#how-an-installation-gets-linked).

That is why these pages can sometimes "heal" after an install finishes in
GitHub even if you did not manually resync every step yourself.

## Typical failure symptoms

When coverage is missing or wrong, users usually see one of these:

- Triggers is empty
- Automations cannot find the installation they expect
- an org you belong to is missing from Settings
- Settings says GitHub is connected, but the status is still `OAuth only`
- Settings shows an App installation, but the repo you care about is missing
  from Projects

## Mental model

Use this rule:

- GitHub sign-in answers "who are you?"
- installation coverage answers "which owners and repos can Mogplex automate?"

If the question is about routing, coverage is the thing that matters.

## Good troubleshooting order

1. Check [Settings](/web/settings) and read the current GitHub status label
2. Confirm the expected owner or org appears in [Installations](/web/installations)
3. Check whether the repo is actually `Trigger-ready` in
   [Projects](/web/spaces)
4. If the App install recently changed, reopen **Settings → Account** so
   discovery runs, or rerun repo sync
5. Retry the exact GitHub event you expect, then confirm it in
   [Observability](/web/observability)
